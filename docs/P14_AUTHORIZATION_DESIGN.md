# Trusted authorization design

Additive table spend_authorizations stores tenant/batch/approver, server-generated UUID, request digest/idempotency key, timestamp and immutable terms. Terms include controlled-test environment, unverified account/org + project identifiers, separately supplied consent-evidence SHA256, models, per-request/total microUSD, request count, effective/deadline (<=24h), round, all four mandatory stops (unknown result/cost anomaly/kill/QA), and batch rate snapshots. No key or raw consent/customer document is stored.

POST /admin/batches/{id}/spend-approvals requires BOTH existing admin header and an authenticated active owner with budget scope. Existing fixed-window rate limits cover it. Batch must belong to owner tenant and authorizing owner, remain open/current, and caps/models/time cannot exceed pinned batch or credential limits. Idempotent repeat returns same immutable record; changed repeat conflicts. Approver comes from authenticated credentials, never body. Separate tenant-scoped GET is read only.

Database CHECK permits only INTERNAL_APPROVAL_ONLY; PostgreSQL FORCE RLS and UPDATE/DELETE/TRUNCATE rejection plus ORM scope/append-only guard protect it. SQLite has update/delete rejection and application scopes; it is not a native RLS substitute. Original SYNTHETIC_TEST_AUTHORIZATION CHECK and immutable batch trigger are unchanged. Internal audit action spend.internal_approval_only logs IDs only.

A client-supplied reference/hash/account string is NOT verified human consent or account ownership. Stored consent_verified=false, account_access=ACCOUNT_ACCESS_NOT_VERIFIED, execution_authorized=false. There is no approval-upgrade API. This phase records policy terms, not a real spend grant, and cannot create EXECUTION_AUTHORIZED. An independent authorization process must authenticate actual human consent/account evidence and append a new reviewed grant in a later authorized change; it cannot mutate these records or synthetic batches. Revoking/expiring current approver or worker must block any future execution.

P1.5 execution contract must recheck effective_at<=now<deadline, exact account/project against environment credential source, model/rate/bound, batch cap/count, reserved attempt and stop rules in the existing transaction; commit DISPATCHING before one send, persist result before settlement. Unknown delivery holds reservation/freezes batch. No automatic retry, fallback, benchmark extension or publication. Existing internal prepare intentionally refuses all current grants and release code remains closed.
